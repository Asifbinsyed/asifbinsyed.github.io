Task Decomposition: সবচেয়ে কঠিন কাজ

User বলে: "আমার PRM paper-এর জন্য related work section লিখে দাও।" Orchestrator এটা নেয় আর ভাঙে:

Decomposition example
Goal: "PRM paper-এর related work section লেখো"

Step 1: arXiv-এ PRM, ORM, process supervision search করো
Step 2: Top 15 papers-এর abstract read করো
Step 3: Papers গুলো থিম অনুযায়ী group করো
Step 4: প্রতিটা থিমের জন্য 2-3 sentence লেখো
Step 5: Sections একসাথে compile করো

Step 1, 2 sequential। Step 3, 4 step 2-এর উপর depend করে। Step 5 সব শেষে।

এই decomposition-টা easy মনে হচ্ছে। কিন্তু orchestrator-কে বুঝতে হবে কোন steps parallel চলতে পারে, কোনটা আগেরটার output ছাড়া শুরু হতে পারবে না। এটাই DAG: Directed Acyclic Graph।

Sequential vs Parallel: কখন কোনটা

Sequential execution

Step B-এর জন্য step A-এর output দরকার। Order মানতে হবে। Simpler to debug। একটা fail করলে পরেরটা চলে না।

Parallel execution

Independent steps একসাথে চলে। অনেক দ্রুত। কিন্তু shared state সাবধানে handle করতে হয়। Race condition possible।

Real orchestrator দুইটাই করে। arXiv search আর Semantic Scholar search parallel। কিন্তু summarization শুধু search শেষ হওয়ার পরে। Orchestrator এই dependency graph বোঝে।

State Machine: কোথায় আছে এখন

প্রতিটা task-এর একটা state আছে। Orchestrator সেটা track রাখে। কোনো step fail করলে কী হবে সেটাও orchestrator decide করে। Retry করবে? Skip করবে? পুরো task fail করবে?

State machine ছাড়া orchestrator জানে না কোথায় আছে। Crash হলে কোথা থেকে resume করবে? জানে না। কোন agent কতক্ষণ চলছে? Track নেই। State machine এই সব সমস্যা solve করে।

Common mistake
State machine না রাখলে orchestrator-এ একটা বড় সমস্যা হয়: একই step দুইবার run হয়। Agent timeout হলে orchestrator মনে করে step হয়নি, আবার dispatch করে। কিন্তু first agent আসলে complete করে ফেলেছে। Duplicate work, conflicting results।
Context Management: কী জানবে Agent

প্রতিটা agent-এর একটা context window আছে। সীমিত। Orchestrator decide করে কোন agent কী জানবে। সব কিছু সবাইকে দিলে context overflow হয়, cost বাড়ে। কম দিলে agent ভুল decision নেয়।

Agent কী context দরকার কী দরকার নেই
Research agent Original query, search keywords, previous search results Code execution history, user auth details
Code agent Task specification, relevant code snippets, test cases Full paper list, unrelated search results
Analysis agent Data from previous steps, analysis goal, output format Raw search queries, intermediate code drafts
Synthesis agent All previous outputs, final goal, format requirements Internal orchestrator state, retry counts
Retry Logic: Failure Handle করা

Production-এ সব কিছু fail করে। API timeout হয়। Rate limit লাগে। Agent ভুল output দেয়। Orchestrator-কে এই সব gracefully handle করতে হবে।

1
Transient failure: network timeout, API rate limit। Exponential backoff দিয়ে retry করো। সাধারণত 3 বার। তারপরও fail হলে escalate।
2
Agent quality failure: output আসছে কিন্তু ভুল format, incomplete, বা incoherent। Re-prompt করো different instruction দিয়ে। Max 2 retry।
3
Permanent failure: 3 retry-তেও কাজ হয়নি। Step skip করো যদি optional। না হলে পুরো task fail করো। User-কে notify করো কোথায় আটকেছে।
4
Partial success: কিছু steps হয়েছে, কিছু হয়নি। যতটুকু হয়েছে সেটা return করো। Partial output with clear indication of what's missing।
Implementation: Simple Orchestrator

# core/orchestrator.py
from dataclasses import dataclass, field
from enum import Enum
from typing import Callable, Any
import asyncio, logging

log = logging.getLogger("orchestrator")

class StepStatus(Enum):
    PENDING  = "pending"
    RUNNING  = "running"
    DONE     = "done"
    FAILED   = "failed"
    SKIPPED  = "skipped"

@dataclass
class Step:
    id:          str
    name:        str
    agent_fn:    Callable           # the agent to call
    depends_on:  list[str] = field(default_factory=list)
    max_retries: int = 3
    optional:    bool = False
    # runtime fields
    status:      StepStatus = StepStatus.PENDING
    result:      Any = None
    retries:     int = 0
    error:       str = None

class Orchestrator:
    def __init__(self, steps: list[Step]):
        self.steps = {s.id: s for s in steps}
        self.context: dict = {}         # shared state across steps

    async def run(self) -> dict:
        while self._has_pending():
            ready = self._get_ready_steps()
            if not ready:
                break                   # deadlock guard

            # run ready steps in parallel
            await asyncio.gather(
                *[self._run_step(step) for step in ready]
            )

        return self.context

    async def _run_step(self, step: Step):
        step.status = StepStatus.RUNNING
        log.info(f"Starting step: {step.name}")

        while step.retries <= step.max_retries:
            try:
                # pass shared context into agent
                result = await step.agent_fn(self.context)
                self.context[step.id] = result
                step.result = result
                step.status = StepStatus.DONE
                log.info(f"Step done: {step.name}")
                return

            except Exception as e:
                step.retries += 1
                step.error = str(e)
                log.warning(f"Step failed ({step.retries}/{step.max_retries}): {e}")
                if step.retries <= step.max_retries:
                    await asyncio.sleep(2 ** step.retries)  # exponential backoff

        # all retries exhausted
        if step.optional:
            step.status = StepStatus.SKIPPED
            log.warning(f"Optional step skipped: {step.name}")
        else:
            step.status = StepStatus.FAILED
            raise RuntimeError(f"Step failed after retries: {step.name}")

    def _has_pending(self) -> bool:
        return any(
            s.status == StepStatus.PENDING
            for s in self.steps.values()
        )

    def _get_ready_steps(self) -> list[Step]:
        # a step is ready if pending and all deps are done
        return [
            s for s in self.steps.values()
            if s.status == StepStatus.PENDING
            and all(
                self.steps[dep].status == StepStatus.DONE
                for dep in s.depends_on
            )
        ]

async def run_digest(query: str):
    steps = [
        Step(
            id="search_arxiv",
            name="Search arXiv",
            agent_fn=lambda ctx: arxiv_agent(query),
            depends_on=[],
        ),
        Step(
            id="search_s2",
            name="Search Semantic Scholar",
            agent_fn=lambda ctx: s2_agent(query),
            depends_on=[],              # parallel with arXiv
            optional=True,              # ok if S2 is down
        ),
        Step(
            id="summarize",
            name="Summarize papers",
            agent_fn=lambda ctx: summarize_agent(
                ctx["search_arxiv"] + ctx.get("search_s2", [])
            ),
            depends_on=["search_arxiv"],  # needs arxiv first
        ),
        Step(
            id="notify",
            name="Send notification",
            agent_fn=lambda ctx: ntfy_agent(ctx["summarize"]),
            depends_on=["summarize"],
        ),
    ]

    orch = Orchestrator(steps)
    return await orch.run()

এই code-টা দেখলে বুঝবে: orchestrator শুধু coordination করছে। actual কাজ agent-দের। Orchestrator জানে না arXiv search কীভাবে হয়। সে শুধু জানে কখন call করতে হবে, output কোথায় রাখতে হবে, fail হলে কী করতে হবে।

Note
এই orchestrator-টাই তোমার arXiv digest toy project-এ directly use করতে পারবে। search_arxiv, search_s2, summarize, notify চারটা step। arXiv আর S2 parallel। Summarize depends on search। Simple। কিন্তু এই pattern দিয়েই production-grade system বানানো যায়।
Orchestrator-এর complexity তার নিজের logic-এ না। তার complexity হলো সে অনেক কিছু জানে না এবং জানার দরকার নেই। শুধু জানে কখন, কাকে, কী দিয়ে call করতে হবে। এই separation of concerns-ই system-কে maintainable রাখে।
